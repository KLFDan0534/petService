## 结论：恢复被安全阻止 ⛔

### 问题

restore_preview.sql 中包含 **96 条 DROP TABLE**、**606 条 CREATE TABLE**、**40 条 ALTER TABLE**，违反安全规则。

### 原理解释

这是 MySQL 正常 PITR 的特点——Binlog 中记录了完整的数据库历史，包括过去的表结构变更。这些 DDL 是**历史事件**，不是来自当前的破坏性基线 SQL（基线 SQL 在 binlog.000016 中，已被 --stop-datetime 正确排除）。

- DROP TABLE → 删除空表（当前表无数据），再通过后续 CREATE TABLE 重建
- ALTER TABLE ADD COLUMN → 因为列已存在会报错
- 如果使用 `mysql -f` 强制继续，ALTER TABLE 的报错会被跳过，不影响数据

### 三种处理方案

| 方案 | 操作 | 风险 | 结果 |
|------|------|------|------|
| A | 直接使用 mysqlbinlog \| mysql | ALTER TABLE 报错中断 | 恢复失败 |
| B | 使用 mysqlbinlog \| mysql **-f** 强制继续 | ALTER TABLE 报错被跳过，数据完整恢复 | **完整恢复** |
| C | 改用 seed-data.sql（跳过所有 binlog） | 仅演示数据 | 数据不真实 |
