## 1. 顺序原则

```
先跑通 → 再读懂 → 才能改
理解一条链路  →  路上发现的 bug 当场修  →  真的缺才补中间件
```

❌ 不要：打开 BUGFIX 清单从头修到尾。修完你只会多 10 个 diff，还是讲不出项目怎么跑。
✅ 要：一次只推一条链路，链路走完，bug 清单自然少几条。

## 2. 什么叫"理解了"（四层，从低到高）

| 层 | 标准 | 怎么自检 |
|---|---|---|
| **L1 能跑** | 知道怎么启动、怎么把这个功能点出来 | 不看文档能启动前后端并点出功能 |
| **L2 能追** | 能说出入口 → 执行顺序 → 数据落到哪张表 | 白纸画出调用链，标出每个方法名 |
| **L3 能解释** | 能说清至少一个设计**为什么这样**，以及不这样会怎样 | 回答"如果去掉这个注解/这层校验会出什么问题" |
| **L4 能改** | 知道改哪个文件、怎么验证、会影响谁 | 说得出验收命令和回归范围 |

**每条链路至少要摸到 L3。** 答辩问的都是 L3。

### 5.3 已确认的三个关键设计

1. **计价服务端权威**：`assertBillingUnitCompatible:1584` / `assertExpectedUnitPrice:1602` / `assertServiceVersionMatches:1623` / `assertMerchantPayloadCompatible:651`。真正的单价来自 `resolvePricePerDay:1641`（`service.price_wsh` 优先）。
2. **day 与 slot 两条平行路径**：`day` 用 `[start_date, end_date)`；`session/hour` 结束时间由服务端算，客户端 `end_time` 只做一致性校验（`:1936`）。折扣判定用 `resolveDiscountDays:1675`，hour 只按 1 天算。
3. **并发保护两层且不对称**：`synchronized`（单 JVM，**事务提交前释放**）+ **仅容量**用 `SELECT ... FOR UPDATE`（`:1881`）。**宠物冲突 `:1849` 没有行锁。**
4. **`synchronized` 释放早于事务提交**（`:543` 的 `@Transactional` 在方法级，提交发生在 `createOrder` 返回后由代理执行）。所以线程 B 拿到锁时，线程 A 的 INSERT 可能还在未提交事务里 → B 的任何普通 SELECT 都看不到它。这是理解第 3 条"为什么加锁了还可能漏"的钥匙。

### 5.4 未决问题（已答，2026-10-27）

> **Q：为什么只有 `ensureKeeperCapacity` 加 `selectByIdForUpdate`，`ensureNoPetDateConflict` 不加？不加锁的那个什么场景会漏检？**
>
> 详细版见 [`docs/下单链路讲解.md`](../docs/下单链路讲解.md) 第 3.4 节。三层答案：
>
> **① 锁锚点**：容量有天然锚点（`max_pets_wsh` 就在 `keeper_wsh` 行上，锁它顺理成章）；宠物冲突没有对应代码，要锁得锁 `pet_wsh` 行，但 `requirePet` 用的是普通 `selectById`（`:1465`）。
>
> **② 顺序（代码事实）**：`:684` 宠物检查在 `:685` keeper 行锁**之前**跑完，完全不受那把锁保护。
>
> **③ 隔离级别（推断，待实测）**：RR 下快照在第一次普通 SELECT 建立（就是 `requirePet`），之后 `FOR UPDATE` 只提供排队、不刷新快照 → 锁后的 `selectCount` 仍读旧数据。所以那把 `FOR UPDATE` 的真实效果可能也有限。
>
> **漏检场景**：多实例部署时 `synchronized` 失效，两个请求同时给同一宠物下重叠日期订单 → 两单都成功。单实例下窗口极窄但存在（要求 B 的 `requirePet` 落在 A 提交前）。
>
> **批量下单能力已下线**：当前为单宠物、单订单模型，一次下单只创建一个订单、只关联一只宠物，不再存在「一个事务里锁多只宠物」的批次顺序死锁问题；单笔下单的宠物冲突检查仍需关注。

## 8. 中间件什么时候才值得加

**默认不加。** 前提是"理解到某处，发现现有方案有明确缺陷，且最小改动能验证"。

| 中间件 | 现状 | 值得加的条件 | 本项目结论 |
|---|---|---|---|
| Redis 缓存 | ✅ 已用（Spring Cache） | — | 已用，只需补失效（X1/X2） |
| RabbitMQ 延迟队列 | ✅ 已用（支付/接单超时） | — | 已用 |
| **唯一索引 / 幂等** | ⚠️ 部分缺失 | MQ 重投有实际风险 | **加**：`notification_wsh` 一条唯一索引（N6） |
| 分布式锁 | ❌ 无（只有 `synchronized` + 一处 DB 行锁） | 多实例 + 有超卖风险 | **不加**。讲清局限即加分 |
| 接口限流 | ❌ 单机 `ConcurrentHashMap` | 有公网真实流量 | **不加**。同上 |
| 本地缓存 Caffeine | ❌ 无 | 有热点 + 能容忍不一致 | **不做** |
| 事务消息 / 本地消息表 | ❌ 无 | 要求"发消息与落库强一致" | **不做**。说清取舍即可 |

> 一句话：**只补 1 条 DDL（N6），其余全部是"讲得清 > 加得上"。**
